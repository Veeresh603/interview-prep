1 Why did you use Redux?
We used Redux because our app had complex shared state across many disconnected components — things like user auth, cart data, and notification counts that needed to be read and updated from anywhere in the tree without prop-drilling.

When Redux makes sense

  • Many components at different levels need the same data
  • State updates are complex — multiple actions affect the same slice
  • Predictable debugging — time-travel debugging with Redux DevTools
  • Team size — strict patterns (actions, reducers) keep large teams consistent

What to say in the interview

Frame it around a real problem: "We had a dashboard where filters, user preferences, and real-time data all needed to be shared across 15+ components in different parts of the tree. Prop-drilling was unmanageable, and Context re-rendered too many components. Redux gave us targeted updates via selectors and a clear audit trail via actions."

Follow-up ready: If they ask "Would you still choose Redux today?" — say "For new projects I'd evaluate Redux Toolkit (much less boilerplate) vs Zustand (simpler API). But Redux remains the right choice when you need middleware, DevTools time-travel, and strict action patterns in a large team."
2 Why React instead of Angular?
React gives us a lightweight view library with freedom to choose our own routing, state management, and build tools, while Angular is a full opinionated framework. React's component model, massive ecosystem, and one-way data flow made it the better fit for our team.

Key differences to mention

  • Learning curve: React — learn JSX + hooks. Angular — learn TypeScript, decorators, modules, DI, RxJS, zones
  • Flexibility: React lets you pick your router, state library, form handling. Angular bundles everything
  • Bundle size: A basic React app starts around 40KB gzipped vs Angular's ~100KB+
  • One-way data flow: React's unidirectional flow is easier to debug than Angular's two-way binding
  • Ecosystem: React's npm ecosystem is significantly larger
Don't bash Angular: Say "Angular is great for enterprise apps with large teams that benefit from opinionated structure. We chose React because our team valued flexibility and our app was more consumer-facing where bundle size and interactivity mattered."
3 What are the stages in the React lifecycle?
React components go through three phases: Mounting (component is created and inserted into DOM), Updating (component re-renders due to state/prop changes), and Unmounting (component is removed from DOM).

Class component lifecycle methods

  1. Mounting: constructor → getDerivedStateFromProps → render → componentDidMount
  2. Updating: getDerivedStateFromProps → shouldComponentUpdate → render → getSnapshotBeforeUpdate → componentDidUpdate
  3. Unmounting: componentWillUnmount

Hooks equivalent (what you should actually use)

function MyComponent({ userId }) {
  // Mounting + Updating: runs after every render
  useEffect(() => {
    fetchUser(userId);
  }, [userId]); // only re-runs when userId changes

  // Mounting only (empty deps)
  useEffect(() => {
    initAnalytics();
    // Unmounting: cleanup function
    return () => cleanupAnalytics();
  }, []);

  return <div>...</div>;
}
Say this: "In modern React, we don't think in lifecycle methods anymore. We think in effects that synchronize with external systems. useEffect replaces componentDidMount, componentDidUpdate, and componentWillUnmount with a single mental model."
4 What hooks have you used?
I regularly use useState, useEffect, useRef, useMemo, useCallback, useContext, and useReducer. I've also built custom hooks for API calls, form handling, debouncing, and local storage sync.

Quick summary of each

  • useState — local component state
  • useEffect — side effects (API calls, subscriptions, DOM manipulation)
  • useRef — mutable value that persists across renders without causing re-renders (DOM refs, timers)
  • useMemo — cache expensive computed values
  • useCallback — cache function references to prevent child re-renders
  • useContext — consume context without nesting Consumer components
  • useReducer — complex state with multiple sub-values or when next state depends on previous

Custom hook example

function useDebounce(value, delay = 300) {
  const [debounced, setDebounced] = useState(value);
  useEffect(() => {
    const timer = setTimeout(() => setDebounced(value), delay);
    return () => clearTimeout(timer);
  }, [value, delay]);
  return debounced;
}

// Usage
const debouncedSearch = useDebounce(searchTerm, 500);
Impress tip: Mention you follow the rules of hooks (only call at top level, only in React functions) and explain why — "React relies on call order to match state slots to useState calls."

10 How do you approach production issues?
Triage first (severity + impact), reproduce the issue, check logs and monitoring, isolate the root cause, apply a fix or hotfix, then do a post-mortem to prevent recurrence.

Step-by-step process

  1. Triage: How many users affected? Is it a blocker? Assign severity (P0/P1/P2)
  2. Quick look: Check error monitoring (Sentry/Datadog), look at recent deploys, check for API errors
  3. Reproduce: Match the user's environment, browser, data. Can I reproduce locally?
  4. Isolate: Is it frontend or backend? Which component/API? Git bisect if needed
  5. Fix: For P0 — hotfix branch, fast-track review, deploy immediately. For P1 — normal PR process
  6. Verify: Confirm fix in staging AND production. Check monitoring for 30 min
  7. Post-mortem: Document root cause, timeline, fix, and prevention measures
Senior answer: "I also set up proactive monitoring — Sentry alerts for new error spikes, performance budgets with alerts, and synthetic monitoring for critical flows. The best production issue is one caught before users report it."

12 How do you perform application performance tuning?
I measure first using Lighthouse, Chrome DevTools, and React Profiler, then optimize the three main bottlenecks: bundle size (code splitting, tree shaking), rendering (memo, virtualization), and network (caching, prefetching, compression).

Performance tuning checklist

Bundle size:

  • Analyze with webpack-bundle-analyzer or source-map-explorer
  • Code-split routes with React.lazy + Suspense
  • Dynamic import heavy libraries (chart libs, date libs)
  • Tree-shake unused exports, replace large deps with smaller ones (moment → date-fns)

Rendering:

  • Profile with React DevTools Profiler — find components that re-render too often
  • Apply React.memo, useMemo, useCallback where needed
  • Virtualize long lists with react-window or tanstack-virtual
  • Debounce search inputs, throttle scroll handlers

Network:

  • Cache API responses (React Query staleTime, HTTP cache headers)
  • Prefetch data for likely next pages (router.prefetch, queryClient.prefetchQuery)
  • Compress images (WebP/AVIF), use responsive images with srcset
  • Enable gzip/brotli compression on the server
Golden rule: "Don't optimize blindly. Measure, identify the bottleneck, fix it, measure again. The React Profiler and Lighthouse are my starting points for every performance investigation."

React Deep Dive

1 How does React rendering work?
React rendering is a two-phase process: the Render phase (calls your component functions to produce a virtual DOM tree) and the Commit phase (applies the minimal set of DOM changes calculated by diffing the old and new trees).

The two phases

  1. Render phase (pure, no side effects): React calls your component function, which returns JSX. React converts this to a Virtual DOM tree. It then diffs this new tree against the previous one to find changes. This phase can be paused/restarted (concurrent mode).
  2. Commit phase (DOM mutations): React applies the calculated changes to the real DOM in one batch. Then it runs useLayoutEffect, then the browser paints, then useEffect runs.
// Timeline of a state update:
setState(newValue)
  → Schedule re-render
  → RENDER PHASE: Call component function, diff VDOM
  → COMMIT PHASE: Apply DOM changes
  → useLayoutEffect runs (synchronous, before paint)
  → Browser paints
  → useEffect runs (asynchronous, after paint)
Key insight: "Rendering" in React does NOT mean updating the DOM. It means calling your component function. The DOM only updates in the commit phase if changes are detected.
2 What causes a React component to re-render?
Four things trigger a re-render: (1) its own state changes via setState, (2) its parent re-renders (regardless of whether props changed), (3) the context it consumes changes, (4) a custom hook's internal state changes.

The biggest misconception

People think "if props didn't change, the child won't re-render." Wrong. By default, when a parent re-renders, ALL its children re-render. You need React.memo to skip re-renders when props are the same.

function Parent() {
  const [count, setCount] = useState(0);
  return (
    <>
      <button onClick={() => setCount(c => c + 1)}>{count}</button>
      <Child name="Alice" />  {/* Re-renders EVERY click! */}
    </>
  );
}

// Fix: wrap with React.memo
const Child = React.memo(function Child({ name }) {
  return <p>{name}</p>; // Now skips re-render if name unchanged
});
3 How do you identify unnecessary re-renders?
Use the React DevTools Profiler to record interactions and see which components re-rendered, how long they took, and why. Enable "Highlight updates when components render" for a quick visual check.

Tools and techniques

  • React DevTools Profiler: Record a session, click on a component → see "Why did this render?" (state change, props change, parent re-render)
  • Highlight updates: React DevTools settings → enable "Highlight updates" — flashing borders show re-renders in real time
  • Console logging: Temporarily add console.log('render', componentName) at the top of the component
  • useWhyDidYouRender: Third-party library that logs the exact prop/state that changed
Not all re-renders are bad. Only optimize when a re-render is: (1) frequent (every keystroke, scroll), (2) expensive (large component trees, heavy computations), or (3) causing visible jank.
4 How would you optimize a slow React application?
Profile first, then attack the three pillars: reduce bundle size (code splitting), reduce render count (memoization), and reduce render cost (virtualization, offloading work).

Optimization checklist

  1. Profile: Lighthouse, React Profiler, bundle analyzer
  2. Code split: React.lazy for routes and heavy components
  3. Memoize: React.memo for expensive children, useMemo for expensive computations
  4. Virtualize: react-window for lists with 100+ items
  5. State colocation: Move state closer to where it's used to limit re-render blast radius
  6. Debounce/throttle: Input handlers, scroll/resize listeners
  7. Web Workers: Offload CPU-heavy tasks (parsing, sorting large datasets)
5 When would you use useMemo?
Use useMemo when you have an expensive computation that you don't want to re-run on every render — things like filtering/sorting large arrays, complex calculations, or creating derived data structures.
function ProductList({ products, filters }) {
  // WITHOUT useMemo: filters 10,000 products on every render
  // WITH useMemo: only recomputes when products or filters change
  const filtered = useMemo(() => {
    return products.filter(p =>
      p.price >= filters.minPrice &&
      p.category === filters.category
    );
  }, [products, filters]);

  return filtered.map(p => <ProductCard key={p.id} product={p} />);
}
Don't overuse it. useMemo itself has overhead (storing previous values, comparing deps). Only use it when the computation is actually expensive. A simple a + b does not need useMemo.
6 When would you use useCallback?
Use useCallback when you pass a function as a prop to a memoized child (React.memo), or when the function is a dependency of useEffect. Without it, a new function reference is created every render, breaking memoization.
const Parent = () => {
  const [count, setCount] = useState(0);

  // Without useCallback: new function every render
  // ExpensiveList re-renders even though React.memo wraps it
  const handleClick = useCallback((id) => {
    console.log('clicked', id);
  }, []); // stable reference

  return (
    <>
      <button onClick={() => setCount(c => c + 1)}>{count}</button>
      <ExpensiveList onClick={handleClick} />
    </>
  );
};

const ExpensiveList = React.memo(({ onClick }) => {
  // Only re-renders if onClick reference changes
  return /* ... 1000 items ... */;
});
useCallback without React.memo is useless. If the child isn't memoized, it'll re-render anyway when the parent re-renders, regardless of whether the function reference is stable.
7 What is the difference between useMemo and useCallback?
useMemo caches the result of calling a function. useCallback caches the function itself. Essentially, useCallback(fn, deps) is equivalent to useMemo(() => fn, deps).
// useMemo: caches the RESULT (the sorted array)
const sorted = useMemo(() => items.sort(compareFn), [items]);

// useCallback: caches the FUNCTION (the handler reference)
const handleClick = useCallback((id) => {
  selectItem(id);
}, [selectItem]);

When to use which

  • useMemo → Expensive computations (filtering, sorting, transforming data)
  • useCallback → Stable function references (event handlers passed to memoized children, deps of useEffect)
8 When does React.memo help?
React.memo helps when a component re-renders often due to its parent, receives the same props most of the time, and is expensive to render (large subtree, complex calculations, or many DOM elements).

When it helps

  • Component is in a frequently-updating parent but its own props rarely change
  • Component renders a large list or complex visualization
  • Component is used many times (e.g., a table cell rendered 500 times)

When it does NOT help

  • Props change on almost every render anyway (memo adds overhead, skips nothing)
  • Component is already cheap to render (simple <span>)
  • Props include objects/arrays created inline (new reference every render defeats memo)
// This DEFEATS React.memo because style is a new object every render
<MemoizedChild style={{ color: 'red' }} />

// Fix: hoist the object or useMemo it
const style = useMemo(() => ({ color: 'red' }), []);
<MemoizedChild style={style} />
9 Can React.memo actually hurt performance?
Yes. React.memo adds overhead — it performs a shallow comparison of all props on every render. If props change frequently, you're paying the comparison cost AND still re-rendering, making it slower than no memo at all.

Cases where memo hurts

  • Props always change: Inline objects, arrays, or functions as props — new reference every render, comparison always fails
  • Cheap components: A simple <span>{text}</span> is cheaper to re-render than to shallow-compare its props
  • Complex props: Many props with nested objects make the shallow comparison expensive but ineffective (shallow compare won't catch deep changes)
Rule of thumb: Only add React.memo when you've profiled and confirmed unnecessary re-renders are causing a performance problem. Premature memoization is a code smell.
10 Explain reconciliation.
Reconciliation is React's diffing algorithm that compares the previous and new Virtual DOM trees to determine the minimal set of DOM operations needed. It uses two heuristics: different element types rebuild the subtree, and keys identify stable elements in lists.

Two core rules

  1. Different type? (<div> → <span>) — Destroy old subtree entirely, build new from scratch. All state in that subtree is lost.
  2. Same type? — Keep the DOM node, update only changed attributes, then recurse into children.

List reconciliation with keys

Without keys, React compares children by position. With keys, React matches by key value — so inserting an item at the top doesn't cause every item to re-render.

Why O(n) not O(n³): A general tree diff is O(n³). React's two heuristics reduce it to O(n) by never comparing across different levels or different types.
11 Why are keys important in React?
Keys let React identify which items in a list have changed, been added, or removed. Without stable keys, React re-renders the entire list when one item changes, destroying component state and causing bugs.
// BAD: index as key
// Inserting at top shifts every index, React updates ALL items
{items.map((item, i) => <Item key={i} {...item} />)}

// GOOD: stable unique ID
// React knows exactly which item was added/removed
{items.map(item => <Item key={item.id} {...item} />)}

What goes wrong with index keys

  • Reordering: React thinks every item changed (index shifted)
  • State bugs: Inputs retain values from the wrong item
  • Performance: Entire list re-renders instead of just the changed item
12 What happens if you use array indexes as keys?
It works fine for static lists that never reorder. But for dynamic lists (sort, filter, add, delete), index keys cause React to mismatch items, destroy/recreate wrong components, lose input state, and trigger unnecessary re-renders.

Visual example of the bug

// Before: [{name: "Alice"}, {name: "Bob"}]
// key=0: Alice, key=1: Bob

// User adds "Charlie" at the top
// After: [{name: "Charlie"}, {name: "Alice"}, {name: "Bob"}]
// key=0: Charlie, key=1: Alice, key=2: Bob

// React sees: key=0 changed "Alice" → "Charlie" (UPDATE)
//             key=1 changed "Bob" → "Alice"     (UPDATE)
//             key=2 is new "Bob"                    (CREATE)
// All 3 items re-render! With stable IDs, only 1 insert needed.
Index keys are only safe when: The list is static (no reorder, add, or delete) AND items have no state (no inputs, no animations).
13 Controlled vs uncontrolled components?
Controlled components store form values in React state (value + onChange), giving React full control. Uncontrolled components let the DOM handle values, and you read them via refs when needed.
// CONTROLLED: React owns the value
function Controlled() {
  const [name, setName] = useState('');
  return <input value={name} onChange={e => setName(e.target.value)} />;
}

// UNCONTROLLED: DOM owns the value
function Uncontrolled() {
  const ref = useRef();
  const handleSubmit = () => console.log(ref.current.value);
  return <input ref={ref} defaultValue="" />;
}

When to use which

  • Controlled: Real-time validation, conditional disabling, formatting input, when you need the value for other UI updates
  • Uncontrolled: File inputs (must be uncontrolled), integrating non-React libraries, simple forms where you only need the value on submit
14 How would you build reusable components?
Design components with a single responsibility, accept flexible props (children, render props, composition), keep styles themeable, and document with Storybook. Think "API design" — your component's props ARE its API.

Principles

  • Composition over configuration: Use children and slots instead of dozens of boolean props
  • Inversion of control: Let the consumer decide what to render (render props, compound components)
  • Sensible defaults: Work out of the box, but allow overrides
  • Forward ref: Allow parent to access the DOM node
  • Spread remaining props: ...rest on the root element for className, aria-*, data-* etc.
// Good: composable, flexible
<Card>
  <Card.Header>Title</Card.Header>
  <Card.Body>Content</Card.Body>
  <Card.Footer><Button>Save</Button></Card.Footer>
</Card>

// Bad: rigid, prop-heavy
<Card title="Title" body="Content" footerButton="Save" />
15 How would you design a large React application?
Feature-based folder structure, clear separation between server state and UI state, a shared component library, strict TypeScript, automated testing at every level, and CI/CD that enforces quality gates.

Architecture pillars

  1. Structure: Feature folders (not file-type folders). Each feature is self-contained with its own components, hooks, API, and state
  2. State strategy: Server state in React Query/SWR, global UI state in Redux/Zustand, local state in useState. Never mix them
  3. Component layers: Design system (atoms) → shared components (molecules) → feature components (organisms) → pages
  4. Type safety: Strict TypeScript with no any, shared API types generated from backend schema
  5. Testing: Unit tests for utils/hooks, integration tests for features, E2E for critical flows
  6. Performance budget: Bundle size limits enforced in CI, Lighthouse checks on PRs
Senior signal: "Architecture is about making the right thing easy and the wrong thing hard. Good folder conventions, strict linting rules, and PR templates enforce quality without relying on individual discipline."

Redux (Critical)

1 Why Redux? (Deep Dive)
Redux provides a single source of truth for global state, predictable state updates via pure reducer functions, powerful debugging with time-travel DevTools, and middleware for handling side effects like API calls.

The three core principles of Redux

  1. Single source of truth: The entire application state lives in one JavaScript object (the store). This makes it easy to serialize, debug, inspect, and hydrate from server
  2. State is read-only: You can never mutate state directly. The only way to change state is to dispatch an action — a plain object describing what happened
  3. Changes via pure functions: Reducers are pure functions that take the previous state + an action and return a brand new state object. No side effects, no mutations, no API calls inside reducers

Why choose Redux over other solutions?

  • Predictable debugging: Every state change has a corresponding action. DevTools show the full action log, state diffs, and let you time-travel (step forward/backward through state changes)
  • Centralized state: When 10+ components across different routes need the same data (auth, cart, notifications), Redux ensures a single consistent copy
  • Middleware pipeline: Intercept every action for logging, analytics, async operations, error tracking — before it reaches the reducer
  • Ecosystem: Redux Toolkit (RTK), RTK Query, redux-persist, Redux DevTools, Reselect, huge community
  • Testability: Reducers are pure functions — pass input, assert output. No mocking needed

Modern Redux with Redux Toolkit (RTK)

import { createSlice, configureStore } from '@reduxjs/toolkit';

// createSlice = reducer + actions in one place
const cartSlice = createSlice({
  name: 'cart',
  initialState: { items: [], total: 0 },
  reducers: {
    addItem(state, action) {
      // RTK uses Immer internally — you CAN "mutate" here
      // (it produces a new immutable state under the hood)
      state.items.push(action.payload);
      state.total += action.payload.price;
    },
    removeItem(state, action) {
      const index = state.items.findIndex(i => i.id === action.payload);
      if (index !== -1) {
        state.total -= state.items[index].price;
        state.items.splice(index, 1);
      }
    },
    clearCart(state) {
      state.items = [];
      state.total = 0;
    },
  },
});

export const { addItem, removeItem, clearCart } = cartSlice.actions;

const store = configureStore({
  reducer: { cart: cartSlice.reducer },
  // RTK adds thunk middleware + dev checks automatically
});

Redux vs alternatives

  • vs Context API: Context re-renders ALL consumers on any change. Redux + useSelector only re-renders components whose selected data changed. Context is for low-frequency updates (theme, auth); Redux for high-frequency shared state
  • vs Zustand: Zustand is simpler, less boilerplate, no Provider needed. Use Zustand for small-medium apps. Redux for large apps that need middleware, DevTools, and RTK Query
  • vs React Query: They solve different problems. React Query manages server state (API cache). Redux manages client/UI state. Best practice: use both together
Senior answer: "I choose Redux when the app has complex shared UI state, needs middleware for side-effect orchestration, and benefits from time-travel debugging. For server data I pair it with React Query. For simple apps, Zustand or even Context is enough — Redux would be overkill."
2 Redux vs Context API?
Context is for passing data down without prop-drilling (theme, locale, auth). Redux is for complex, frequently-updated state that many components read. Context re-renders ALL consumers on any change; Redux with selectors only re-renders components that read the changed slice.

Key differences

  • Performance: Context re-renders every consumer when the value changes. Redux + useSelector only re-renders if the selected slice changed
  • Debugging: Redux has DevTools with action logs and time-travel. Context has nothing built-in
  • Middleware: Redux can intercept actions for async logic, logging, analytics. Context can't
  • Boilerplate: Context is simpler to set up. Redux (even with RTK) requires more structure
Common mistake: Using Context as a state manager for frequently-updated data (like form state or real-time data). Context is a dependency injection mechanism, not a state manager.
3 When should you NOT use Redux?
Don't use Redux for server/cache state (use React Query), local component state (use useState), form state (use React Hook Form), or when your app is simple enough that prop-drilling or Context works fine.

You probably don't need Redux when

  • Most state is server data — React Query/SWR handles caching, refetching, and stale data better
  • State is only used by 1-2 components — just use useState
  • The app is small (under 10 components sharing state)
  • You're adding Redux just because "it's what we always do" — that's cargo culting
4 What belongs in Redux and what belongs in component state?
Put state in Redux if multiple disconnected components need it, it should survive navigation, or you need to track its changes in DevTools. Keep state local if only one component (or its direct children) uses it.

Decision framework

  • Redux: User auth, shopping cart, notification count, global filters, feature flags, UI preferences (theme, sidebar open)
  • Component state: Form input values, dropdown open/close, tooltip visibility, animation states, modal open/close
  • React Query: Any data fetched from an API (product list, user profile, dashboard stats)
  • URL state: Current page, search params, active tab (use the router)
Litmus test: "If I navigate away and come back, should this state still be there?" If yes → Redux or URL. If no → local state.
5 Explain Redux data flow.
User interaction → dispatch an action → action hits middleware (for side effects) → reducer creates new state → store updates → connected components re-render with new data. It's a strict unidirectional circle.
// 1. Component dispatches an action
dispatch({ type: 'cart/addItem', payload: { id: 1, name: 'Shoes' } });

// 2. Middleware intercepts (optional - logging, async, etc.)

// 3. Reducer produces new state (pure function)
function cartReducer(state = initialState, action) {
  switch (action.type) {
    case 'cart/addItem':
      return { ...state, items: [...state.items, action.payload] };
    default:
      return state;
  }
}

// 4. Store holds the new state
// 5. useSelector in components picks up the change
const cartItems = useSelector(state => state.cart.items);
Key principle: State is never mutated directly. Reducers always return a NEW state object. This is what makes Redux predictable and enables time-travel debugging.
6 What is middleware in Redux? (Deep Dive)
Middleware sits between dispatching an action and the reducer receiving it. It can intercept, modify, delay, or replace actions — commonly used for async operations (API calls), logging, error reporting, and analytics.

The middleware signature explained

// Every Redux middleware has this curried signature:
const myMiddleware = (store) => (next) => (action) => {
  // store — has getState() and dispatch()
  // next  — calls the NEXT middleware in the chain (or the reducer if last)
  // action — the dispatched action object

  // Do something BEFORE the reducer runs
  console.log('Before:', store.getState());

  const result = next(action); // pass action down the chain

  // Do something AFTER the reducer runs
  console.log('After:', store.getState());

  return result;
};

How the middleware chain works

// When you dispatch an action, it flows through middleware like a pipeline:
//
// dispatch(action)
//   → Middleware 1 (logger)
//     → Middleware 2 (auth)
//       → Middleware 3 (thunk)
//         → REDUCER (produces new state)
//       ← returns to Middleware 3
//     ← returns to Middleware 2
//   ← returns to Middleware 1
//
// Each middleware can:
//   1. Pass the action along:  next(action)
//   2. Modify the action:      next({ ...action, extra: 'data' })
//   3. Swallow the action:     (don't call next — action never reaches reducer)
//   4. Dispatch NEW actions:   store.dispatch(differentAction)

Practical middleware examples

// 1. AUTH TOKEN INJECTION — attach token to every API action
const authMiddleware = (store) => (next) => (action) => {
  if (action.type.startsWith('api/')) {
    const token = store.getState().auth.token;
    action.meta = { ...action.meta, token };
  }
  return next(action);
};

// 2. ERROR REPORTING — catch action errors, send to Sentry
const errorMiddleware = (store) => (next) => (action) => {
  try {
    return next(action);
  } catch (err) {
    Sentry.captureException(err, { extra: { action, state: store.getState() } });
    throw err;
  }
};

// 3. ANALYTICS — track specific user actions
const analyticsMiddleware = (store) => (next) => (action) => {
  if (action.type === 'cart/checkout') {
    analytics.track('Checkout Started', {
      itemCount: store.getState().cart.items.length,
    });
  }
  return next(action);
};

// 4. API MIDDLEWARE — centralized API call handler
const apiMiddleware = (store) => (next) => async (action) => {
  if (action.type !== 'API_CALL') return next(action);

  const { url, method, onSuccess, onError } = action.payload;
  store.dispatch({ type: 'api/loading' });

  try {
    const data = await fetch(url, { method }).then(r => r.json());
    store.dispatch({ type: onSuccess, payload: data });
  } catch (err) {
    store.dispatch({ type: onError, payload: err.message });
  }
};

Built-in middleware in Redux Toolkit

  • Redux Thunk: Included by default in RTK. Lets you dispatch functions for async logic
  • Immutability check: Warns if you accidentally mutate state outside Immer (dev only)
  • Serializability check: Warns if you put non-serializable values (functions, class instances) in state or actions (dev only)
  • RTK Listener middleware: Like a lightweight Saga — respond to actions with async logic, cancellation, conditions
// Applying middleware in RTK
const store = configureStore({
  reducer: rootReducer,
  middleware: (getDefaultMiddleware) =>
    getDefaultMiddleware()       // includes thunk + dev checks
      .concat(authMiddleware)    // add custom middleware
      .concat(analyticsMiddleware),
});

When to write custom middleware

  • Do write: Cross-cutting concerns that apply to many actions (auth, logging, analytics, API normalization)
  • Don't write: Logic specific to one feature — use a thunk or RTK listener instead
  • Rule of thumb: If you're checking action.type for one specific action, it probably belongs in a thunk. If you're intercepting a category of actions, middleware is the right place
Interview tip: "Middleware is Redux's plugin system. It gives you a single point to add cross-cutting concerns without touching every reducer or component. Think of it like Express middleware for your state management."
7 Redux Thunk vs Redux Saga?
Thunk uses async/await for simple async flows (fetch data, dispatch result). Saga uses generator functions for complex flows (race conditions, retries, debouncing, channels, parallel tasks). Thunk is simpler; Saga is more powerful.

Thunk example

// Simple, easy to understand
const fetchUser = (id) => async (dispatch) => {
  dispatch({ type: 'user/loading' });
  try {
    const user = await api.getUser(id);
    dispatch({ type: 'user/loaded', payload: user });
  } catch (err) {
    dispatch({ type: 'user/error', payload: err.message });
  }
};

Saga example

// More powerful: can cancel, retry, race, debounce
function* fetchUserSaga(action) {
  try {
    const user = yield call(api.getUser, action.payload);
    yield put({ type: 'user/loaded', payload: user });
  } catch (err) {
    yield put({ type: 'user/error', payload: err.message });
  }
}

function* watchFetchUser() {
  yield takeLatest('user/fetch', fetchUserSaga); // auto-cancels previous
}

When to use which

  • Thunk: Simple CRUD, straightforward API calls, 90% of use cases
  • Saga: Complex workflows — polling, WebSocket orchestration, race conditions, retry with backoff, multi-step transactions
8 Why did your project use Redux Saga?
We used Saga because we had complex async workflows: polling for real-time data updates, handling race conditions when users rapidly switch tabs, and orchestrating multi-step form submissions where each step depended on the previous API response.

Specific scenarios where Saga shined

  • takeLatest: When a user types fast in a search box, takeLatest auto-cancels previous API calls — only the last one runs. Thunk can't cancel.
  • Polling: while(true) { yield call(fetchData); yield delay(5000); } — clean polling loop that's easy to start/stop
  • Parallel fetches: yield all([call(fetchA), call(fetchB)]) — fetch multiple resources in parallel
  • Error retry: Automatic retry with exponential backoff using a simple loop
Be honest: "If I were starting fresh today, I'd evaluate RTK Query for data fetching and only reach for Saga if we had genuinely complex orchestration needs. Saga adds significant complexity."
9 How do you handle API calls with Redux?
Modern approach: use RTK Query (built into Redux Toolkit) which handles fetching, caching, and cache invalidation automatically. Classic approach: dispatch loading/success/error actions via thunk or saga middleware.

RTK Query approach (recommended)

// Define the API
const api = createApi({
  baseQuery: fetchBaseQuery({ baseUrl: '/api' }),
  endpoints: (build) => ({
    getUsers: build.query({ query: () => '/users' }),
    addUser: build.mutation({
      query: (user) => ({ url: '/users', method: 'POST', body: user }),
      invalidatesTags: ['Users'], // auto-refetch list
    }),
  }),
});

// Use in component
const { data, isLoading, error } = useGetUsersQuery();

Classic thunk pattern

// Three action types per API call
const fetchUsers = createAsyncThunk('users/fetch', async () => {
  const response = await fetch('/api/users');
  return response.json();
});

// Reducer handles pending/fulfilled/rejected automatically
extraReducers: (builder) => {
  builder
    .addCase(fetchUsers.pending, (state) => { state.loading = true; })
    .addCase(fetchUsers.fulfilled, (state, action) => {
      state.loading = false;
      state.users = action.payload;

    .addCase(fetchUsers.rejected, (state, action) => {

}
10 How do you prevent unnecessary Redux re-renders?
Use granular selectors that return only the data each component needs, use createSelector for derived data (memoized selectors), and never create new objects/arrays inside selectors.
// BAD: returns a new array every time (new reference = re-render)
const items = useSelector(state =>
  state.items.filter(i => i.active)
);

// GOOD: memoized selector with Reselect/RTK
const selectActiveItems = createSelector(
  state => state.items,
  items => items.filter(i => i.active)
); // Only recomputes when state.items changes

const items = useSelector(selectActiveItems);

Rules for efficient selectors

  • Select the smallest piece of state possible
  • Never do useSelector(state => state) — re-renders on ANY state change
  • Use createSelector for any filtering, mapping, or transformation
  • Use shallowEqual as second arg to useSelector if you must return an object
11 What are selectors?
Selectors are functions that extract and optionally transform specific pieces of state from the Redux store. They act as a stable API between your store shape and your components, and can be memoized to avoid unnecessary recalculations.
// Simple selector
const selectUser = (state) => state.auth.user;

// Memoized selector with derived data
const selectCartTotal = createSelector(
  (state) => state.cart.items,
  (items) => items.reduce((sum, item) => sum + item.price * item.qty, 0)
);

// Parameterized selector
const selectItemById = createSelector(
  (state) => state.items.list,
  (_, itemId) => itemId,
  (list, itemId) => list.find(i => i.id === itemId)
);

Why selectors matter

  • Encapsulation: If store shape changes, update the selector, not every component
  • Performance: Memoized selectors prevent recalculation and re-renders
  • Reusability: Same selector used across many components
  • Testability: Pure functions, easy to unit test
12 How would you structure Redux in a large application?
Feature-based slices with Redux Toolkit. Each feature owns its slice (reducer + actions + selectors). Use code-splitting with store.injectReducer for lazy-loaded features. Keep the store flat and normalized.
store/
  index.ts            # configureStore, root reducer
  middleware.ts       # custom middleware

features/
  auth/
    authSlice.ts      # createSlice: reducer + actions
    authSelectors.ts  # all selectors for auth
    authApi.ts        # RTK Query endpoints or thunks
  cart/
    cartSlice.ts
    cartSelectors.ts
  dashboard/
    dashboardSlice.ts
    dashboardSelectors.ts

Key patterns

  • Normalize state: Use entities pattern ({ ids: [], entities: {} }) instead of arrays — O(1) lookups
  • createEntityAdapter: RTK provides this out of the box for CRUD operations
  • Slice isolation: Each slice only manages its own state. Cross-slice logic goes in thunks or listener middleware
13 What problems occur when Redux state becomes too large?
Large Redux state leads to memory bloat, slow serialization (DevTools), unnecessary re-renders from broad selectors, slow reducer updates on deeply nested state, and difficulty debugging because too much unrelated data is in one place.

Common problems and solutions

  • Memory: Storing entire API responses → only store what you need, paginate, evict stale data
  • DevTools slow: Huge state serialization → exclude large slices from DevTools in production
  • Re-renders: Selectors reading too much → granular selectors, createSelector
  • Staleness: Cached data never refreshed → use TTL, listen for visibility change to refetch
  • Complexity: Everything in Redux → move server state to React Query, move local state to useState
Modern rule: "Redux should only hold true global UI state. Server data belongs in a data-fetching library. Most apps have way too much in Redux because they started before React Query existed."
14 Does Redux state persist when you refresh the browser?
No. Redux state lives in JavaScript memory (a variable in the running app). When you refresh the browser, the entire JavaScript context is destroyed and re-created, so all Redux state resets to its initialState.

Why state is lost

// Redux store is just a JS object in memory
const store = configureStore({
  reducer: { cart: cartReducer },
  // initialState of cartReducer = { items: [], total: 0 }
});

// User adds items → state = { cart: { items: [shoes, shirt], total: 150 } }
// User hits F5 (refresh)
// → Browser destroys the entire JS execution context
// → React app re-mounts from scratch
// → configureStore runs again with initialState
// → state = { cart: { items: [], total: 0 } }  ← everything gone!

Solution 1: redux-persist (most common)

import { persistStore, persistReducer } from 'redux-persist';
import storage from 'redux-persist/lib/storage'; // uses localStorage

const persistConfig = {
  key: 'root',
  storage,
  whitelist: ['auth', 'cart'],    // ONLY persist these slices
  // blacklist: ['notifications'], // or exclude specific slices
};

const persistedReducer = persistReducer(persistConfig, rootReducer);

const store = configureStore({
  reducer: persistedReducer,
  middleware: (getDefault) =>
    getDefault({ serializableCheck: false }), // redux-persist uses non-serializable actions
});

const persistor = persistStore(store);

// In your App component:
// <PersistGate loading={<Spinner />} persistor={persistor}>
//   <App />
// </PersistGate>

Solution 2: Manual localStorage (simple cases)

// Save to localStorage on every state change
store.subscribe(() => {
  const { auth, cart } = store.getState();
  localStorage.setItem('appState', JSON.stringify({ auth, cart }));
});

// Load from localStorage on app start
const savedState = JSON.parse(localStorage.getItem('appState') || '{}');
const store = configureStore({
  reducer: rootReducer,
  preloadedState: savedState,
});

What to persist vs what to refetch

  • Persist (survives refresh): Auth tokens, user preferences (theme, language), shopping cart, draft form data, onboarding progress
  • Don't persist (refetch from API): User profile data, product lists, dashboard stats, notifications — these go stale quickly; let React Query refetch fresh data on mount
  • Never persist: Loading states, error messages, modal open/close, temporary UI state

localStorage vs sessionStorage

  • localStorage: Persists even after closing the browser tab/window. Use for auth tokens, user preferences
  • sessionStorage: Cleared when the tab is closed. Use for sensitive data like payment flow state
Security note: Never store sensitive data (passwords, credit card numbers) in localStorage/Redux state. Auth tokens are acceptable but should have short expiry + refresh token rotation.
Senior answer: "Redux state is ephemeral by design — it's just a JS variable. For persistence, I use redux-persist with a whitelist of only the slices that need to survive a refresh. Server data doesn't need persistence because React Query re-fetches it on mount anyway."

1 Explain closures.
A closure is a function that remembers the variables from its outer scope even after the outer function has returned. Every function in JavaScript forms a closure over its lexical environment.
function createCounter() {
  let count = 0; // This variable is "closed over"
  return {
    increment: () => ++count,
    getCount: () => count,
  };
}

const counter = createCounter();
counter.increment(); // 1
counter.increment(); // 2
counter.getCount();  // 2
// 'count' still exists because the returned functions hold a reference to it

Real-world uses

  • Data privacy: Variables in the closure are truly private (no access from outside)
  • Factory functions: Create configured functions like createLogger('auth')
  • Event handlers: Callbacks that remember the context they were created in
  • React hooks: useState, useEffect — closures capture state values at render time
Stale closure bug in React: When useEffect captures an old state value because the dependency array is missing the state variable. This is the #1 hooks bug.
2 Explain the event loop.
JavaScript is single-threaded. The event loop continuously checks if the call stack is empty, then picks the next task from the microtask queue (Promises), then the macrotask queue (setTimeout, events) to execute.

Execution order

  1. Execute all synchronous code (call stack)
  2. Drain the microtask queue (Promise callbacks, queueMicrotask, MutationObserver)
  3. Pick ONE task from the macrotask queue (setTimeout, setInterval, I/O, UI events)
  4. Repeat from step 2
console.log('1');                          // sync
setTimeout(() => console.log('2'), 0);     // macrotask
Promise.resolve().then(() => console.log('3')); // microtask
console.log('4');                          // sync

// Output: 1, 4, 3, 2
// Sync first, then microtasks, then macrotasks
Why this matters: Understanding the event loop explains why setTimeout(fn, 0) doesn't run immediately, why Promises resolve before timeouts, and why blocking the call stack freezes the UI.
3 Microtask vs macrotask?
Microtasks (Promises, queueMicrotask) run immediately after the current task completes and before the browser renders or picks up the next macrotask (setTimeout, setInterval, I/O). The entire microtask queue is drained before moving on.

Key difference

  • Microtasks: Promise.then/catch/finally, queueMicrotask, MutationObserver. All microtasks run before the browser paints.
  • Macrotasks: setTimeout, setInterval, setImmediate (Node), requestAnimationFrame, I/O events, UI events
Danger: If a microtask keeps scheduling more microtasks, the macrotask queue starves and the browser can't repaint — the page freezes.
4 Promise vs async/await?
They do the same thing. async/await is syntactic sugar over Promises that makes asynchronous code read like synchronous code. Under the hood, an async function always returns a Promise.
// Promise chains
fetchUser(id)
  .then(user => fetchOrders(user.id))
  .then(orders => displayOrders(orders))
  .catch(err => showError(err));

// Same logic with async/await (cleaner)
async function loadOrders(id) {
  try {
    const user = await fetchUser(id);
    const orders = await fetchOrders(user.id);
    displayOrders(orders);
  } catch (err) {
    showError(err);
  }
}

When to prefer which

  • async/await: Sequential async operations, try/catch error handling, most common choice
  • Promise.then: When chaining is more readable, or running inside a non-async context
  • Promise.all: When you need parallel execution (can use with await too: await Promise.all([...]))
5 Promise.all() vs Promise.allSettled()?
Promise.all() fails fast — if ANY promise rejects, the whole thing rejects immediately. Promise.allSettled() waits for ALL promises to complete and gives you the result of each, whether fulfilled or rejected.
// Promise.all: first rejection kills everything
try {
  const [a, b, c] = await Promise.all([fetchA(), fetchB(), fetchC()]);
} catch (err) {
  // If fetchB fails, you lose fetchA and fetchC results too
}

// Promise.allSettled: get all results regardless
const results = await Promise.allSettled([fetchA(), fetchB(), fetchC()]);
// [
//   { status: 'fulfilled', value: dataA },
//   { status: 'rejected', reason: Error },
//   { status: 'fulfilled', value: dataC }
// ]

When to use which

  • Promise.all — All-or-nothing: loading a page where ALL data is required
  • Promise.allSettled — Best-effort: dashboard widgets where each can fail independently
6 Explain hoisting.
Hoisting moves variable and function declarations to the top of their scope during compilation. var declarations are hoisted and initialized to undefined. let/const are hoisted but NOT initialized — accessing them before declaration throws a ReferenceError (temporal dead zone).
console.log(a); // undefined (var is hoisted + initialized to undefined)
var a = 5;

console.log(b); // ReferenceError: Cannot access 'b' before initialization
let b = 5;      // b is hoisted but in the "temporal dead zone"

greet();        // "Hello!" (function declarations are fully hoisted)
function greet() { console.log("Hello!"); }

sayBye();       // TypeError: sayBye is not a function
var sayBye = function() { console.log("Bye!"); };
// var sayBye is hoisted (undefined), but the assignment isn't
7 var vs let vs const.
var is function-scoped and hoisted (legacy, avoid it). let is block-scoped and reassignable. const is block-scoped and cannot be reassigned (but objects/arrays it points to can still be mutated).
// var: function-scoped, hoisted, can cause bugs
for (var i = 0; i < 3; i++) {
  setTimeout(() => console.log(i), 100); // 3, 3, 3 (shared i)
}

// let: block-scoped, each iteration gets its own i
for (let i = 0; i < 3; i++) {
  setTimeout(() => console.log(i), 100); // 0, 1, 2
}

// const: cannot reassign, but can mutate
const arr = [1, 2];
arr.push(3);    // OK: [1, 2, 3]
arr = [4, 5];   // TypeError: Assignment to constant variable
Modern rule: Default to const. Use let only when reassignment is needed. Never use var.
8 Explain this.
In JavaScript, this is determined by HOW a function is called, not where it's defined. In a method call, it's the object. In a regular function, it's window/undefined. Arrow functions inherit this from their enclosing scope.
const obj = {
  name: 'Alice',
  greet() { console.log(this.name); },        // 'Alice' (method call)
  greetArrow: () => console.log(this.name),   // undefined (arrow: outer this)
};

obj.greet();        // 'Alice'
obj.greetArrow();   // undefined (this = window/module)

const fn = obj.greet;
fn();               // undefined (lost context, this = window)
fn.call(obj);       // 'Alice' (explicit binding)

Rules in order of priority

  1. new — this is the new instance
  2. call/apply/bind — this is the explicitly passed object
  3. Method call (obj.fn()) — this is obj
  4. Plain call (fn()) — this is window (sloppy) or undefined (strict)
  5. Arrow function — inherits this from enclosing lexical scope
9 Shallow copy vs deep copy.
A shallow copy duplicates the top-level properties but still shares references to nested objects. A deep copy recursively duplicates everything, creating a completely independent clone.
const original = { name: 'Alice', address: { city: 'NYC' } };

// Shallow copy: spread operator
const shallow = { ...original };
shallow.address.city = 'LA';
console.log(original.address.city); // 'LA' (shared reference!)

// Deep copy: structuredClone (modern)
const deep = structuredClone(original);
deep.address.city = 'LA';
console.log(original.address.city); // 'NYC' (independent)

Methods

  • Shallow: { ...obj }, Object.assign(), [...arr], arr.slice()
  • Deep: structuredClone() (best), JSON.parse(JSON.stringify()) (loses functions, dates, undefined)
Why this matters in React/Redux: React state updates require new references to trigger re-renders. Redux reducers must return new state objects. Understanding copy depth prevents bugs where you accidentally mutate state.
10 Debouncing vs throttling.
Debouncing delays execution until a pause in events (fires once after the user stops). Throttling limits execution to at most once per time interval (fires at a steady rate during continuous events).
// Debounce: fires ONCE, 300ms after the user stops typing
function debounce(fn, delay) {
  let timer;
  return (...args) => {
    clearTimeout(timer);
    timer = setTimeout(() => fn(...args), delay);
  };
}

// Throttle: fires at most once every 200ms during scrolling
function throttle(fn, limit) {
  let inThrottle;
  return (...args) => {
    if (!inThrottle) {
      fn(...args);
      inThrottle = true;
      setTimeout(() => inThrottle = false, limit);
    }
  };
}

When to use which

  • Debounce: Search input (wait for user to stop typing), window resize handler, auto-save
  • Throttle: Scroll events (infinite scroll), mouse move tracking, rate-limiting API calls
11 Event bubbling vs capturing.
When you click an element, the event travels in two phases: Capturing (top-down, from window to target) and Bubbling (bottom-up, from target back to window). By default, event listeners fire during the bubbling phase.
<div id="outer">
  <div id="inner">
    <button id="btn">Click</button>
  </div>
</div>

// Click the button:
// CAPTURING: window → document → div#outer → div#inner → button
// TARGET: button (event fires on the target)
// BUBBLING: button → div#inner → div#outer → document → window

// Listen during capturing phase:
outer.addEventListener('click', handler, true); // third arg = capture
// Listen during bubbling phase (default):
outer.addEventListener('click', handler);       // or false
  • event.stopPropagation() — stops the event from continuing up/down
  • event.preventDefault() — prevents the browser default (form submit, link navigation)
12 Event delegation.
Instead of attaching an event listener to every child element, attach ONE listener to the parent and use event.target to determine which child was clicked. This is more memory-efficient and works for dynamically added elements.
// BAD: 1000 listeners for 1000 list items
items.forEach(item => {
  item.addEventListener('click', handleClick);
});

// GOOD: 1 listener on the parent
document.getElementById('list').addEventListener('click', (e) => {
  const item = e.target.closest('li'); // find the clicked li
  if (item) handleClick(item.dataset.id);
});

Benefits

  • Memory: 1 listener instead of N
  • Dynamic elements: Works for items added later (no need to re-attach listeners)
  • Cleanup: Only 1 listener to remove
React connection: React uses event delegation internally — it attaches a single event listener to the root DOM node and delegates all events. That's why event.nativeEvent exists.
13 How would you optimize expensive JavaScript?
Profile first with Chrome DevTools Performance tab, then apply: Web Workers for CPU-heavy tasks, requestAnimationFrame for visual updates, chunking long tasks with setTimeout/scheduler.yield, and efficient data structures.

Techniques

  • Web Workers: Move heavy computation (parsing, sorting 100K items, image processing) off the main thread
  • Task chunking: Break a loop processing 10,000 items into chunks of 100, yielding to the browser between chunks
  • requestAnimationFrame: Batch visual DOM updates to sync with the browser's paint cycle
  • Memoization: Cache function results for repeated calls with same arguments
  • Efficient algorithms: Use Map/Set for O(1) lookups instead of Array.find O(n)
// Chunking a long task to avoid blocking
async function processLargeArray(items) {
  const CHUNK_SIZE = 100;
  for (let i = 0; i < items.length; i += CHUNK_SIZE) {
    const chunk = items.slice(i, i + CHUNK_SIZE);
    processChunk(chunk);
    // Yield to browser between chunks

1 Why Next.js instead of React alone?

2 SSR vs SSG vs ISR?
SSR renders HTML on every request (always fresh). SSG renders HTML at build time (fastest, but stale until rebuild). ISR is the best of both — serves static HTML but revalidates in the background after a time interval.

Comparison

  • SSG (Static Site Generation): HTML built at next build. Served from CDN. Fastest. Best for content that rarely changes (blog, docs, marketing)
  • SSR (Server-Side Rendering): HTML generated on the server per request. Always up-to-date. Best for personalized/dynamic pages (dashboard, search results)
  • ISR (Incremental Static Regeneration): Serves stale static page, triggers background rebuild after revalidate seconds. Best for product pages, news articles — "mostly static, occasionally updated"

3 When would you choose SSR?
Choose SSR when the page content depends on the request (user-specific data, cookies, search params), needs to be always up-to-date, and SEO matters. Examples: personalized dashboards, search results pages, checkout flows.

SSR is the right choice when

  • Content is user-specific (can't pre-build for every user)
  • Data changes frequently and stale data is unacceptable
  • Page uses request data (cookies, headers, auth tokens)
  • SEO is critical AND content is dynamic
Downside: SSR is slower than SSG because it runs server code on every request. Use caching headers (Cache-Control) to mitigate. Consider ISR if "slightly stale" is acceptable.

5 What is hydration?
Hydration is the process where React takes the server-rendered static HTML and "activates" it by attaching event listeners and making it interactive. The browser shows the HTML immediately (fast first paint), then React makes it clickable.

How it works

  1. Server renders HTML string and sends it to the browser
  2. Browser shows the HTML immediately (fast first contentful paint)
  3. JavaScript bundle loads
  4. React walks the existing DOM, attaches event handlers, and reconciles its Virtual DOM with the actual DOM — this is "hydration"
  5. Page is now fully interactive
Key insight: During hydration, React does NOT recreate the DOM. It reuses the existing server-rendered DOM nodes and just attaches the interactivity layer on top.
6 What causes hydration mismatch?
Hydration mismatch happens when the HTML rendered on the server differs from what React produces on the client. Common causes: using Date.now(), Math.random(), window/localStorage during render, or rendering based on browser-only APIs.

Common causes

  • Time-based values: new Date() on server vs client gives different timestamps
  • Random values: Math.random() produces different results
  • Browser APIs: window.innerWidth, localStorage, navigator don't exist on server
  • User-agent based rendering: Showing mobile vs desktop layout based on UA
  • Extensions: Browser extensions modifying the DOM before hydration

How to fix

// Use useEffect for browser-only values
function MyComponent() {
  const [mounted, setMounted] = useState(false);
  useEffect(() => setMounted(true), []);

  // Server and client both render the same fallback initially
  if (!mounted) return <div>Loading...</div>;

  // After hydration, render browser-specific content
  return <div>Width: {window.innerWidth}</div>;
}

// Or use suppressHydrationWarning for intentional mismatches
<time suppressHydrationWarning>{new Date().toLocaleString()}</time>
7 Server Component vs Client Component?
Server Components run only on the server — they can access databases, file systems, and secrets directly, with zero client-side JavaScript. Client Components run on the client (and server for SSR) — they can use state, effects, event handlers, and browser APIs.

Key differences

  • Server Components (default in App Router): No useState, no useEffect, no onClick, no browser APIs. CAN import server-only modules, read databases, access env secrets. Zero bundle size impact.
  • Client Components ("use client"): Full React interactivity. Hooks, events, browser APIs. Code ships in the JS bundle.

8 What happens when you use "use client"?
The "use client" directive marks the boundary where React transitions from Server Components to Client Components. The marked component AND all its imports become part of the client JavaScript bundle.

What actually happens

  1. Next.js sees "use client" and marks this file as a client boundary
  2. The component is still server-rendered for SSR (HTML generation)
  3. But its JavaScript code is included in the client bundle for hydration
  4. All components imported by this file are also treated as Client Components
  5. Server Components can still be passed as children (via the children prop) — they stay on the server
// This pattern keeps ServerComponent on the server!

}

12 How does Next.js caching work?
Next.js has four caching layers: Request Memoization (deduplicates identical fetch calls in one render), Data Cache (persists fetch results across requests), Full Route Cache (caches rendered HTML/RSC payload), and Router Cache (client-side cache for visited routes).

The four caching layers

  1. Request Memoization: If you call fetch('/api/user') in 5 different Server Components during the same render, Next.js makes only 1 actual HTTP request. Automatic, per-request, no config needed.
  2. Data Cache: Fetch results are stored on the server across requests. Persists until revalidated. Control with { next: { revalidate: 60 } } or { cache: 'no-store' }.
  3. Full Route Cache: For static routes, the entire rendered HTML + RSC payload is cached at build time. Served from CDN on subsequent requests. Invalidated by revalidation.
  4. Router Cache: Client-side in-memory cache. When you navigate back to a previously visited page, it shows instantly from the client cache instead of making a server request.
// No caching (always fresh)
fetch('https://api.example.com/data', { cache: 'no-store' });

// Revalidate every 60 seconds
fetch('https://api.example.com/data', {
  next: { revalidate: 60 }
});

// Cache forever (default for static data)
fetch('https://api.example.com/data');
// equivalent to { cache: 'force-cache' }

How to opt out of caching

  • export const dynamic = 'force-dynamic' — opt out at the route level
  • { cache: 'no-store' } — opt out per fetch
  • revalidatePath() / revalidateTag() — on-demand cache invalidation
  • Using cookies() or headers() in a Server Component auto-opts into dynamic rendering
Common gotcha: Developers expect data to be fresh but Next.js caches aggressively by default. If your page shows stale data, check whether you need cache: 'no-store' or a revalidate interval.

1 What are common useEffect pitfalls and how do you avoid them?
The three big pitfalls are infinite loops (missing or wrong dependency array), stale closures (referencing outdated state), and missing cleanup (subscriptions, timers, abort controllers left dangling).

1. Infinite loops

// BUG: runs infinitely because `data` is new every render
useEffect(() => {
  fetch('/api/items').then(res => res.json()).then(setData);
}, [data]); // data changes → re-fetch → data changes → ...

// FIX: fetch once on mount, or use a stable trigger
useEffect(() => {
  fetch('/api/items').then(res => res.json()).then(setData);
}, []); // empty deps = run once

2. Stale closures

// BUG: always logs the initial count
useEffect(() => {
  const id = setInterval(() => console.log(count), 1000);
  return () => clearInterval(id);
}, []); // count is stale

// FIX: add count to deps, or use a ref
useEffect(() => {
  const id = setInterval(() => console.log(count), 1000);
  return () => clearInterval(id);
}, [count]);

3. Missing cleanup

// BUG: if component unmounts before fetch completes → state update on unmounted component
useEffect(() => {
  fetch('/api/user').then(res => res.json()).then(setUser);
}, []);

// FIX: use AbortController
useEffect(() => {
  const controller = new AbortController();
  fetch('/api/user', { signal: controller.signal })
    .then(res => res.json())
    .then(setUser)
    .catch(err => {
      if (err.name !== 'AbortError') throw err;
    });
  return () => controller.abort();
}, []);

Other pitfalls

  • Object/array deps: useEffect(() => {}, [{ a: 1 }]) runs every render because objects are compared by reference. Use primitive deps or useMemo
  • Missing deps: ESLint's exhaustive-deps rule catches this — always enable it
  • Async directly in useEffect: You can't make the callback async. Define an inner async function and call it
Senior signal: "In new projects, I prefer React Query or SWR for data fetching instead of raw useEffect — they handle caching, cancellation, retries, and race conditions out of the box."
2 How do you handle loading and error states when calling APIs?
I track three states — loading, error, and data — either manually with useState or (preferably) with React Query/SWR which manage this automatically, plus I add skeleton UIs, error boundaries, and retry logic.

Manual approach (with useState)

function UserProfile({ userId }) {
  const [data, setData] = useState(null);
  const [loading, setLoading] = useState(true);
  const [error, setError] = useState(null);

  useEffect(() => {
    const controller = new AbortController();
    setLoading(true);
    setError(null);

    fetch(`/api/users/${userId}`, { signal: controller.signal })
      .then(res => {
        if (!res.ok) throw new Error(`HTTP ${res.status}`);
        return res.json();
      })
      .then(setData)
      .catch(err => {
        if (err.name !== 'AbortError') setError(err.message);
      })
      .finally(() => setLoading(false));

    return () => controller.abort();
  }, [userId]);

  if (loading) return <Skeleton />;
  if (error) return <ErrorBanner message={error} onRetry={...} />;
  return <Profile data={data} />;
}

Better: React Query

4 If debounced API calls return out of order, how do you ensure only the last result is used?
The core problem is a race condition: user types "ab" (API call #1), then "abcd" (API call #2), but call #1's response arrives AFTER call #2's. Without handling, you'd display stale results for "ab" instead of "abcd". Solution: cancel previous requests or ignore stale responses.

The problem visualized

// User types: a → ab → abc → abcd (debounced to "ab" and "abcd")
//
// Timeline:
// t=0ms    User types "ab" → debounce timer starts
// t=300ms  Debounce fires → API call #1: search("ab")
// t=500ms  User types "abcd" → debounce timer starts
// t=800ms  Debounce fires → API call #2: search("abcd")
// t=1200ms API call #2 responds (fast server) → shows "abcd" results ✓
// t=1500ms API call #1 responds (slow!) → OVERWRITES with "ab" results ✗
//
// Result: User sees results for "ab" even though they typed "abcd"!

Solution 1: AbortController (cancel previous request)

function useSearch(query) {
  const [results, setResults] = useState([]);
  const controllerRef = useRef(null);

  useEffect(() => {
    if (!query) return;

    // Cancel the PREVIOUS request before making a new one
    controllerRef.current?.abort();
    controllerRef.current = new AbortController();

    fetch(`/api/search?q=${query}`, {
      signal: controllerRef.current.signal,
    })
      .then(res => res.json())
      .then(setResults)
      .catch(err => {
        if (err.name !== 'AbortError') console.error(err);
      });

    return () => controllerRef.current?.abort(); // cleanup on unmount
  }, [query]); // query is already debounced

  return results;
}

Solution 2: Ignore stale responses (request ID)

function useSearch(query) {
  const [results, setResults] = useState([]);
  const latestRequestRef = useRef(0);

  useEffect(() => {
    if (!query) return;

    const requestId = ++latestRequestRef.current; // increment for each new request

    fetch(`/api/search?q=${query}`)
      .then(res => res.json())
      .then(data => {
        // Only update if this is still the latest request
        if (requestId === latestRequestRef.current) {
          setResults(data);
        }
        // else: stale response, silently ignore
      });
  }, [query]);

  return results;
}

5 What are interceptors and how do you use them?
Interceptors are functions that run automatically before every request is sent or after every response is received. They let you centralize cross-cutting concerns like attaching auth tokens, refreshing expired tokens, global error handling, and request/response logging — without repeating code in every API call.

Axios request interceptor (attach auth token)

import axios from 'axios';

const api = axios.create({ baseURL: '/api' });

// REQUEST interceptor — runs before every request
api.interceptors.request.use(
  (config) => {
    const token = localStorage.getItem('accessToken');
    if (token) {
      config.headers.Authorization = `Bearer ${token}`;
    }
    // Add request timestamp for logging
    config.metadata = { startTime: Date.now() };
    return config;
  },
  (error) => Promise.reject(error)
);

Axios response interceptor (error handling + token refresh)

// RESPONSE interceptor — runs after every response
api.interceptors.response.use(
  (response) => {
    // Log response time
    const duration = Date.now() - response.config.metadata.startTime;
    console.log(`${response.config.method.toUpperCase()} ${response.config.url} — ${duration}ms`);
    return response;
  },
  async (error) => {
    const originalRequest = error.config;

    // 401 Unauthorized → try refreshing the token
    if (error.response?.status === 401 && !originalRequest._retry) {
      originalRequest._retry = true; // prevent infinite retry loop

      try {
        const { data } = await axios.post('/api/auth/refresh', {
          refreshToken: localStorage.getItem('refreshToken'),
        });
        localStorage.setItem('accessToken', data.accessToken);
        originalRequest.headers.Authorization = `Bearer ${data.accessToken}`;
        return api(originalRequest); // retry the original request
      } catch (refreshError) {
        // Refresh failed → force logout
        localStorage.clear();
        window.location.href = '/login';
        return Promise.reject(refreshError);
      }
    }

    // Global error handling
    if (error.response?.status === 500) {
      toast.error('Server error. Please try again later.');
    }
    if (error.response?.status === 403) {
      toast.error('You do not have permission for this action.');
    }

    return Promise.reject(error);
  }
);

How to achieve the same with fetch (wrapper pattern)

// Since fetch has no built-in interceptors, create a wrapper
async function apiFetch(url, options = {}) {
  // REQUEST "interceptor"
  const token = localStorage.getItem('accessToken');
  const config = {
    ...options,
    headers: {
      'Content-Type': 'application/json',
      ...(token && { Authorization: `Bearer ${token}` }),
      ...options.headers,
    },
  };

  let response = await fetch(url, config);

  // RESPONSE "interceptor" — handle 401
  if (response.status === 401) {
    const refreshed = await refreshToken();
    if (refreshed) {
      config.headers.Authorization = `Bearer ${localStorage.getItem('accessToken')}`;
      response = await fetch(url, config); // retry
    } else {
      window.location.href = '/login';
    }
  }

  if (!response.ok) throw new Error(`HTTP ${response.status}`);
  return response.json();
}

Common interceptor use cases

  • Auth token injection: Attach JWT to every request automatically
  • Token refresh: On 401, refresh the token and retry the original request transparently
  • Global error handling: Show toast for 500s, redirect on 403, logout on expired sessions
  • Request/response logging: Log URL, method, duration, status for debugging
  • Request cancellation: Auto-cancel duplicate requests
  • Loading indicators: Track active request count for global loading spinners
  • Data transformation: Convert snake_case API responses to camelCase for frontend
Senior signal: "Interceptors are the API layer's middleware. I set them up once in a centralized API client, and every component that uses that client gets auth, error handling, and logging for free. Components should never deal with tokens or 401s directly."

  2. Be specific: "I'm blocked on the user API endpoint — it's returning 500 for the /profile route. I've checked the request payload and it matches the Swagger spec. I need backend to investigate. This blocks the profile page, due Thursday."
  3. Show what you tried: Listing your attempts shows initiative and gives the other person context to help faster
  4. Propose alternatives: "While waiting, I can work on the settings page instead, or I can mock the API response and build the UI in parallel"
  5. Escalate if needed: If a blocker isn't resolved in a reasonable time, escalate to the tech lead or scrum master — that's their job
Anti-pattern: "I was blocked for 3 days but didn't tell anyone." This is a red flag in any interview. Always show you communicate proactively.
3 Are you comfortable working directly with client stakeholders?
Yes, absolutely. I've regularly participated in client calls, demos, and requirement discussions. I translate technical concepts into business language and keep stakeholders informed about progress, risks, and trade-offs.

How I work with clients

  • Demos: I present sprint deliverables to clients, walking through features from the user's perspective (not technical jargon)
  • Requirement clarification: When specs are ambiguous, I ask targeted questions with options: "Should the filter persist across sessions, or reset on page reload? Option A is simpler; Option B needs backend storage."
  • Setting expectations: If a requested feature is complex, I explain the trade-off: "We can do a basic version in this sprint and enhance it next sprint, or wait and deliver the full version in two sprints."
  • Status updates: I keep updates concise and focused on what matters to the client: what's done, what's in progress, any risks
Key message: "I see client communication as part of my job, not a distraction from coding. Understanding the 'why' behind requirements helps me build better solutions and avoid rework."
4 Tell me about a time you disagreed with a technical decision — how did you handle it?
I present my concerns with data and specific trade-offs, listen to the other perspective, and if the team decides differently, I commit fully to the chosen approach — disagree and commit.

Example (STAR format)

Situation: "The team lead wanted to use Redux for all state management in a new dashboard project, including server data (API responses)."

Task: "I believed this would lead to excessive boilerplate and stale data bugs, based on my experience in a previous project."

Action:

  • I didn't argue in the meeting — I prepared a comparison document: Redux-for-everything vs. Redux + React Query
  • Showed concrete examples: 40 lines of Redux code (action, reducer, thunk, selector) vs. 5 lines of React Query for the same API call
  • Highlighted risks: manual cache invalidation, no automatic refetch on focus, no retry logic
  • Built a small prototype of one feature both ways, shared it with the team

Result: "The team agreed to use React Query for server state and keep Redux only for global UI state. This reduced our state management code by ~60% and eliminated a whole class of stale-data bugs."

Key principles

  • Data over opinions: Back your position with benchmarks, code samples, or documentation
  • Respect the process: Present your case, but don't undermine the decision if the team goes another way
  • Disagree and commit: "Once the team decides, I give it 100%. I don't say 'I told you so' if it doesn't work out — I help fix it."
  • Pick your battles: Not every disagreement is worth escalating. Save your capital for decisions with real impact
Senior signal: "Technical disagreements are healthy — they mean the team cares. The red flag is when nobody disagrees, because that means nobody is thinking critically."
