The Return Address Bug That Only Broke the Second Time

Tricky BugMulti-Brand LogicProduction Fix

🧠 Understand It Simply

The Problem: A customer returns Item A successfully. Then tries to return Item B from the same order — but it silently fails. The return address goes as an empty {} object.

Why It Happened: When the return dialog closed after the 1st return, it only hid itself (set visibility to false). It never told the parent component to reset the address state. So the 2nd return started with stale, empty data.

Your Fix: Made the dialog's close handler also call handleBackClick() to properly reset parent state. Added a Babyshop Malaysia fallback to read address from fulfillment data when the address step is skipped.

Think of it like: Filling a form, submitting it, then opening the form again — but the form still has "submitted" state instead of being fresh. You need a "reset" after each submission.

State Reset After Multi-Step Flow Silent Failure = Worst UX Brand-Specific Edge Cases

💪 Confidence Builder — Key Phrases to Use

  • "customer escalation" — shows it was a real production issue affecting customers
  • "wrote a failing test first" — shows TDD discipline
  • "silent failure in a critical user journey" — shows you think from the customer's perspective
  • "raised it in our sprint retrospective" — shows process improvement mindset
  • "added to our Definition of Done" — shows lasting team impact
HOW TO START (SETTING THE SCENE)
"So this one came in as a customer escalation — our support team noticed a pattern of complaints where customers were saying 'I can't submit my return.' Our Product Owner flagged it as a P1 defect in the sprint backlog. The user journey was: a customer goes to order details, selects items to return, picks a return pickup address, and submits. It worked perfectly the first time. But when the same customer tried to do a second partial return on the same order — say they returned a shirt first, and now wanted to return shoes — the whole thing silently failed. The API rejected it because the return address was going through as an empty object. So the acceptance criteria was clear: customers must be able to do multiple partial returns on the same order without failure."
WHAT MADE IT TRICKY
"The tricky part was — our existing test coverage didn't have a scenario for sequential returns. The happy-path user story — 'customer returns one item' — passed every time. But the edge case — 'customer returns a second item from the same order' — was never part of the acceptance criteria on the original story. Also, the error wasn't visible to the user — the API just rejected it silently because the address payload was {}. From the customer's perspective, they clicked submit and nothing happened — no error message, no feedback. That's the worst kind of bug: a silent failure in a critical user journey."
HOW I DEBUGGED AND FIXED IT
"First thing I did was reproduce the defect locally and understand the exact user journey that was breaking. Then I wrote a failing test that captured the broken behavior — simulate a first return completing, then initiate a second return and assert the address payload is not empty. That gave me a red test to work against.

Then I traced the data flow. The Order Details Summary manages return flow state — selected items, address details, return reasons. The root cause: after the first return completed, the dialog was closing without resetting return flow state. So on the second attempt, the address was stale and empty.

My fix had two parts. First, when the refund options dialog closed, I made it also call handleBackClick() to properly reset the parent state — so the next user journey starts clean. Second, I added a fallback for Babyshop Malaysia — because their address step is sometimes skipped (different return regulations), so I fall back to reading the shipping address from the fulfillment data. Both changes made my test go green, and I added it as a permanent regression test."
THE RESULT
"Fix went out as a hotfix within the same sprint. Zero recurrence in production — I monitored Grafana for 48 hours post-deploy to confirm. But the bigger win was the process improvement. I raised it in our sprint retrospective as a systemic issue: multi-step flows weren't resetting state on completion. We added a new item to our team's Definition of Done checklist: 'any multi-step user journey (return, exchange, checkout) must have a regression test covering the repeat-flow scenario.' Also, the Babyshop Malaysia fallback taught the team that in a multi-brand system, you can't assume every brand follows the same user journey — acceptance criteria need to be validated per brand-country."

🔧 Technical Details (If They Probe Deeper)

  • Component: orderDetailsSummary.js — class component with complex return flow state
  • returnAddressMapper() received {...addressSource} — spread was fine, but addressSource was empty on second run
  • Babyshop MY: if (concept==="babyshop" && country==="my" && empty) → fallback to fulfillment[0].address
  • Dialog close: changed to wrapper that also calls handleBackClick() for proper parent state reset
  • Root cause: state not properly initialized between user flows — classic "second-run" bug

Pre-Checkout Stock Validation — Preventing "Ghost Orders"

Checkout GuardFull Redux FlowCustomer Trust

🧠 Understand It Simply

The Problem: Customer spends 5 minutes in checkout (address, delivery slot, payment) → hits "Place Order" → gets bounced back to cart because an item went out of stock during checkout. Terrible experience.

Your Solution: Check stock BEFORE the customer leaves the cart page. If something is out of stock, show a modal with options: "Save for Later" or "Remove."

The Full Flow You Built:
1. Customer clicks "Checkout" → 2. API call validates stock for all cart items → 3a. All pass? Proceed to checkout. 3b. Any fail? Show OOS modal with images/sizes. 3c. API itself fails? Let them through (graceful degradation).

Think of it like: A bouncer at the door of a restaurant checking reservations BEFORE you sit down and order, instead of telling you to leave after you've already eaten appetizers.

Full Redux: Action → Saga → Reducer → UI Graceful Degradation Feature-Flagged Rollout

💪 Confidence Builder — Key Phrases to Use

  • "ghost orders" — memorable name the PO used, shows product vocabulary
  • "graceful degradation" — never make the experience WORSE than baseline
  • "feature-flagged, brand-by-brand rollout" — shows progressive delivery
  • "cartReducer listens for the same fulfilled action" — shows Redux architecture depth
  • "giving customers agency" — Save for Later or Remove, not a confusing redirect
HOW TO START (SETTING THE SCENE)
"So we had a frustrating pattern in production — customers would fill their cart, go through checkout, enter their address, pick a payment method, hit 'Place Order'… and then get bounced back to the cart page with an out-of-stock error. The backend returned a FAILED_INVENTORY_CHECK failure type and our saga redirected them to /cart?err=outOfStock. From the customer's perspective, they'd just wasted five minutes on a checkout that was never going to succeed. The Product Owner called these 'ghost orders' — orders that look real but can never be fulfilled — and made it a sprint goal to stop them before they reach the payment stage."
WHAT MADE IT INTERESTING
"The challenge wasn't just calling an API — it was orchestrating an async validation inside an already complex checkout flow. The cart page has two checkout entry points: rightPanel.js on desktop and stickyCheckout.js on mobile — both needed the same logic but they're separate components. Also, we couldn't block the user with a loading spinner forever — if the stock validation API itself failed, we needed graceful degradation: let them proceed and let the backend catch it at order time as before. And the whole thing had to be feature-flagged behind isCartStockValidationEnabled so we could roll it out brand by brand."
WHAT I BUILT
"I built the full Redux flow for this feature. The API layer (stockValidationApi.js) does a POST to /api/cart-operations/cart/{cartId}/validate-stock — sends the cart ID and gets back each item marked with a stockValidationStatus of PASSED or FAILED.

The saga handles the async call, updates the stockValidationReducer through four states: IDLE → LOADING → SUCCESS or FAILURE. On success, the cartReducer also listens for the same fulfilled action — it builds a Map of item IDs to validation statuses and merges them into existing cart items. So the cart state gets enriched without refetching the entire cart.

In the UI, when the customer clicks 'Checkout', I set a pendingValidation flag and dispatch the request. A useEffect watches the reducer status. If any item has status FAILED, it opens our OOS modal (oosModalInfo.js) showing the out-of-stock items with images, sizes, and prices — with two clear actions: 'Save for Later' or 'Remove All'. If all items pass, it proceeds to checkout. If the API itself fails, it gracefully degrades — lets them through."
THE RESULT
"The feature rolled out behind a feature flag — first on Max Fashion, then Centrepoint and Home Centre. Ghost orders dropped significantly because customers now find out at the cart stage, not after five minutes of checkout. The OOS modal gives them agency — save for later or remove — instead of just a confusing redirect. The graceful degradation means we never make the experience worse than it was before. I demoed this in our sprint review and the PO immediately asked to fast-track rollout to all brands."

🔍 Technical Quick Reference (for follow-ups)

  • API: stockValidationApi.js → POST /cart/{cartId}/validate-stock
  • Redux flow: Action → Saga → stockValidationReducer (IDLE/LOADING/SUCCESS/FAILURE) + cartReducer merges status per item
  • UI orchestration: pendingValidation state + useEffect watches reducer — opens OOS modal or proceeds
  • OOS Modal: oosModalInfo.js — shows failed items with Save For Later / Remove All
  • Feature flag: isCartStockValidationEnabled — brand-by-brand rollout
  • Graceful degradation: API failure → proceed to checkout anyway
  • Dual entry points: Same logic in rightPanel.js (desktop) and stickyCheckout.js (mobile)

💬 Follow-up Questions They Might Ask

"Because the customer experience is completely different. Before, they'd fill out their address, pick a delivery slot, enter card details, hit 'Place Order' — and then get bounced back. Listing Page Performance Win — LRU Caching for Search API

PerformanceRedux ArchitectureUX Improvement

🧠 Understand It Simply

The Problem: Customer browses "Men's T-Shirts" page 1 → goes to page 2 → goes back to page 1 → full API call again with a loading spinner. Slow and wasteful.

Your Solution: Built an LRU (Least Recently Used) cache in Redux. When fetching page 1, also prefetch page 2 in the same API call. Serve page 2 instantly from cache. Cap the cache at 3 entries to control memory.

How LRU Works (explain this simply):
Think of a shelf that holds only 3 books. When you access a book, it goes to the front. When a 4th book arrives, the book at the back (oldest accessed) falls off. That's LRU — keeps the most recently used data, drops the oldest.

Three Pieces:
1. Cache Key — strips page number from URL so all pages of same category share a key.
2. Reducer — stores entries + tracks access order. Evicts oldest when over limit.
3. API Layer — checks cache first. Miss? Fetch multiple pages in one call, cache them, return just the requested page.

HOW TO START (SETTING THE SCENE)
"Our product listing pages — categories, search results — are powered by Bloomreach Search API. Every time a customer pages through results or changes a filter, we fire an API call. The problem was: a customer browsing 'Men's T-Shirts' would go to page 2, then come back to page 1 — and we'd hit the API again even though we already had that data. On slow connections in the Gulf region, that's a visible loading delay every time they navigate. The Product Owner wanted smoother pagination — instant back-and-forth between pages. So our sprint goal was to reduce redundant search API calls and make pagination feel instant."
THE DESIGN CHALLENGE
"We can't just cache everything forever — product listings are dynamic: prices change, items go out of stock, promotions rotate. And we can't let the cache grow unbounded because that eats mobile memory. We needed a bounded, smart cache that keeps the most recently viewed pages and evicts the oldest ones. The insight was: if we're calling the API anyway, why not prefetch multiple pages at once and serve subsequent pages from cache?"
WHAT I BUILT
"I built a client-side LRU cache backed by Redux. Three pieces working together.

First, the cache key. generateUrlCacheKey() takes the current URL, strips the pagination parameter (p=X), so all pages of the same category share the same base key. The actual cache key combines this with the batch start page.

Second, the reducer. brSearchCacheReducer maintains an entries object mapping cache keys to response data, and a keyOrder array tracking LRU order. On every access, it promotes the key to the end. When the array exceeds MAX_CACHE_ENTRIES (configurable from backend, default 3), it evicts from the front — classic LRU. The max size comes from sizeOfBRDataLRUCache in our config API, so the backend team can tune it without a deploy.

Third, the API layer. brMultiSearchApi.js checks the Redux cache before making a network call. On a cache hit, it calls extractPageFromResponse() to slice out just the requested page. On a cache miss, it fetches with a larger batch size (configurable pages at once), caches the full response, and returns just the requested page. The consumer gets the same data shape either way."
THE RESULT
"When a customer browses page 1, we silently prefetch pages 1 and 2 in one call. When they hit 'Next Page', page 2 renders instantly from cache — no spinner, no delay. Going back to page 1? Also instant. The cache is capped at 3 entries, so memory stays bounded. For our Gulf markets where mobile bandwidth is variable, this made a noticeable difference in perceived performance. The backend can tune cache size and prefetch count remotely — no frontend deploy. The PO said it was one of those features where customers don't notice when it works, but they definitely noticed the slowness when it didn't."

🔍 Technical Quick Reference (for follow-ups)

  • Cache key: generateUrlCacheKey() strips ?p=X from URL → combined with batch start page
  • Reducer: brSearchCacheReducer — entries (data map) + keyOrder (LRU array) + configurable max
  • LRU eviction: push(key) on access, shift() when over limit + delete entries[oldest]
  • Batch prefetch: noOfBRPagesToCache (default 2) pages per call → extractPageFromResponse() slices
  • Config-driven: sizeOfBRDataLRUCache + readBRDataFromCache — tunable without deploy
  • Cache hit: Check entries[cacheKey] → if hitsPerPage matches, return sliced data + LRU promotion
  • Clear on navigation: clearBrSearchCache() resets on category/search change

💬 Follow-up Questions They Might Ask

"Why Redux for cache and not React Query or SWR?"▼
"Our entire app uses Redux + Redux-Saga for all data fetching. Introducing React Query just for this one feature would add a new dependency and mental model mismatch for the team. The LRU logic in the reducer is about 40 lines — simple, testable, consistent with how everything else works. For an existing large codebase, consistency wins over novelty."
"What about stale data? How do you handle cache invalidation?"▼
"Three strategies. First, LRU eviction — old entries get pushed out naturally. Second, clearBrSearchCache() is dispatched when the customer changes category or search query, so they always get fresh results. Third, readBRDataFromCache in config lets us disable caching entirely for a brand — a remote kill switch without a deploy."
"How does extractPageFromResponse work?"▼
"The API returns, say, 80 products for 2 pages of 40. extractPageFromResponse calculates the offset within the batch, slices docs from offset × hitsPerPage, and sets the start value so the downstream searchPageMapper computes the correct page number without knowing it came from cache. numFound is preserved for correct pagination controls."
"What's the memory impact on mobile?"▼
"That's why the cache is bounded. Default 3 entries, each maybe 50-100KB of JSON — worst case about 300KB. Negligible on any modern phone. And because it's configurable from the backend, if we ever see memory pressure, we can drop it to 2 or 1 without a code deploy."

The 60-Second Walkthrough

🎤 How to say it

“Our pipeline has two parts — CI and CD, both written as YAML files right in the repo.

CI (the build side): When a developer merges code, the CI pipeline kicks off automatically. It installs dependencies with Yarn, runs SonarQube to check code quality, then builds a Docker image. After that, Snyk scans the image for security problems. If anything serious is found, the build stops right there — the code doesn’t go forward. If everything is clean, it saves the Docker image as an artifact.

CD (the deploy side): The CD pipeline picks up that artifact, pushes the image to Azure Container Registry, and uses Helm to deploy it to our Kubernetes clusters. One command deploys to all three brand namespaces — Max, Home Centre, and Centrepoint. After deployment, a notification goes to our Teams channel so the whole squad knows what went out.

For production, we also have disaster recovery — the pipeline automatically spins up a backup cluster, deploys there too, then powers it down.”

🎙️ Common CI/CD Interview Questions — Simple Answers

"What tools do you use for CI/CD?"▼
“Azure DevOps for pipelines, Docker for containerization, Helm for Kubernetes deployments, Azure Container Registry for storing images, and AKS (Azure Kubernetes Service) for running them. For quality, we have SonarQube for code analysis and Snyk for container security scanning. And New Relic for monitoring in production.”
"Walk me through your deployment pipeline."▼
“When code merges, Azure Pipelines runs our CI job. It installs Node 14 and Yarn, does a yarn install with a frozen lockfile, then SonarQube scans for code quality. Next it builds a multi-stage Docker image — one stage for dependencies, one to build the Next.js app, and a final lightweight stage for production. Then Snyk scans the image — if it finds high-severity issues, the build breaks. The image gets saved as a tar file and published as a pipeline artifact.

The CD pipeline downloads that artifact, retags the image for the target Azure Container Registry, pushes it, then runs helm upgrade into AKS — once per brand namespace. After deploy, a Teams webhook notifies the squad with commit details and which namespaces got updated.”
"How does the Docker image get built?"▼
“We use a multi-stage Dockerfile. First stage installs dependencies with Yarn. Second stage copies the source code and runs next build to compile the app. Third stage creates a lightweight production image using node:14-alpine — it only has the built files, the server, and production dependencies. No dev tools, no source code. It runs as a non-root user called nextjs for security, and listens on port 4000.”
"How do you handle different environments?"▼
“We have config files for each environment — like build.uat6.js, build.prod.js, build.preprod.js. Before the build, the pipeline copies the right config file into place with a simple cp config/build.uat6.js config/build.js, then runs next build. So the same code builds differently depending on the target environment. Each environment also has its own Helm values file — so the same Docker image gets deployed with different settings per brand and per environment.”
"How many environments do you have?"▼
“Around 7 UAT environments (uat1 through uat7), a performance testing environment, pre-production, and then production. Production itself is split by brand — Max Fashion, Home Centre, Centrepoint, and eMax each have their own Kubernetes cluster and namespace. We also have disaster recovery clusters for production brands.”
"What about security in your pipeline?"▼
“Three layers. SonarQube catches code-level issues — bugs, code smells, complexity — during the build. Snyk scans the Docker image for known vulnerabilities, and it acts as a build breaker if it finds anything high-severity. And the Docker image itself runs as a non-root user, so even if something got in, it has minimal permissions. We also have AI-powered code review on every pull request that catches issues before code even merges.”
"Do you monitor production? How do you know if something breaks?"▼
“Yes, New Relic. It’s loaded right at the start of our Express server — it’s literally the first require statement. It tracks every request, response time, and errors. Distributed tracing is turned on, so we can follow a request across services. If something goes wrong after a deployment, we see it in real time. After deploying a fix, I check New Relic to confirm error rates dropped — that’s how I know the fix actually worked for customers.”
